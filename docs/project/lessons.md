# 纠错与反思

`docs/project/lessons.md` 记录用户对 AI 的纠正，以及 AI 在工作中发现并修正的错误。每次开工必须先完整阅读本文件。

## 记录规则

- 每次真实纠正后立即新增一条，不积压、不凭空编造。
- 固定格式：**现象 → 原因 → 防止规则**。
- “防止规则”必须具体、可执行，并在后续工作中持续遵守。
- 如果纠正形成长期项目规则，同时更新 `AGENTS.md`。

## 记录

### 2026-08-23 · 访谈问题过于抽象

现象 → AI 用“输出结构固定到什么程度”“不适用环节是否保留”等抽象措辞提问，用户无法直观判断并要求举例。

原因 → AI 只描述了格式概念，没有用同一道具体考研数学题展示不同输出效果。

防止规则 → 此后的需求访谈只要涉及抽象格式、交互或风格差异，就先给出简短、具体、可对比的实例，再用一个明确问题让用户判断。

### 2026-08-23 · 根目录重命名后补丁路径失效

现象 → 项目根目录从 `KaoYan` 重命名为 `DaXueShenMai` 后，仍绑定旧工作区路径的内置补丁调用无法读取当时位于根目录的进度文档（现为 `docs/project/progress.md`）。

原因 → 根目录名称改变了，但当前任务的补丁工作区没有同步刷新。

防止规则 → 以后重命名项目根目录前先完成所有待写文档；重命名后先在新目录验证读取与补丁编辑能力，再继续修改文件。

### 2026-08-23 · 不得猜测阅卷得分点

现象 → AI 在确认判题范围时提出了“按考研阅卷方式估算得分并指出得分点”，用户指出这类内容很容易引发幻觉。

原因 → 没有具体、权威的评分细则时，模型无法可靠还原真实阅卷规则，估分会把推测包装成事实。

防止规则 → `dxsm-math` 只依据题干、数学定理和可检查的推导判断步骤与结果；不估分、不猜得分点。任何信息不足或无法可靠验证的内容都应明确说明并向用户补充询问，禁止无依据生成。

### 2026-08-23 · 主推导不使用引用块

现象 → AI 用 Markdown 引用符号 `>` 包裹完整的逐步数学推导，用户认为可读性不高。

原因 → 引用块会增加视觉缩进并呈现为附注样式，不适合承载公式密集的主线推导。

防止规则 → 数学解题主线使用编号小标题、普通正文和居中的独立展示公式；说明文字保持左对齐。引用块只用于真正引用用户原话或题干片段，不用于包裹完整解答。

### 2026-08-23 · 区分题干缺失与条件不足型考点

现象 → AI 在举例时把“输入不清晰或题干残缺”和“题目完整但现有条件无法推出目标结论”混为同一种情况。

原因 → AI 只关注了信息不足，没有先判断这种不足是否正是题目要求考生识别的数学结论。

防止规则 → 先判断题目语义是否完整：识别结果有歧义或疑似缺字时向用户追问；题目完整且考查条件能否推出结论时，直接依据充分性分析作答，并在需要时给出反例，不擅自要求补充条件。

### 2026-08-23 · 不引入无关的 API Key 概念

现象 → AI 在讨论 Skill 测试时直接提到 API Key、费用和自动调用模型，让用户误以为项目运行需要密钥。

原因 → AI 没有先说明 Skill 由 Codex 或安装后的 Agent 直接执行，把可选的云端自动化测试方案与项目本身混在了一起。

防止规则 → 先明确 `dxsm-math` 本身不需要 API Key，也不保存密钥。只有用户明确要求独立的云端模型测试脚本时才讨论 API 凭据；v1 测试由当前 Codex 会话或安装后的 Agent 执行。

### 2026-08-23 · 错误地将 AGENTS.md 降级为历史文件

现象 → AI 在压缩上下文胶囊中错误降低了 `AGENTS.md` 的规范地位，与用户要求其作为持续维护的仓库执行规范相冲突。

原因 → AI 把一次关于旧指令适用性的上下文判断错误扩大成了对整个文件地位的永久否定，没有回到 `AGENTS.md` 本身核对“活文档”定位，也没有区分“某条旧指令被替换”和“整份执行规范失效”。

防止规则 → 任何单条规则被用户替换时，只修改受影响条款，不得推断整份 `AGENTS.md` 失效。每次开工必须先读 `docs/project/lessons.md` 和 `AGENTS.md`；生成上下文胶囊、权威顺序或交接说明时，必须明确 `AGENTS.md` 是持续生效的执行规范，并搜索全仓库确认没有把它排除在规范来源之外。

### 2026-08-24 · rg 默认模式不支持回顾断言

现象 → AI 在迁移文档后的路径审计中直接向 `rg` 传入回顾断言，命令因默认正则引擎不支持 lookbehind 而失败。

原因 → AI 没有先判断表达式是否需要 PCRE2，也没有优先使用足以完成任务的简单兼容搜索。

防止规则 → 使用 `rg` 设计审计命令时优先采用默认引擎支持的简单表达式；确实需要 lookaround 时显式加入 `--pcre2`。命令失败后先确认没有产生写入，再以更简单的兼容表达式重跑。

### 2026-08-24 · 控制字符和双重转义导致补丁拒绝

现象 → AI 第一次直接修补含原始 CR 的损坏 LaTeX，补丁 hunk 被控制字符拆行；第二次改用 `String.raw` 时又把 Markdown 反引号前的转义斜杠保留进补丁上下文。两次补丁均被完整拒绝，没有产生部分写入。

原因 → AI 把控制字符恢复、LaTeX 转义和 Markdown 上下文混在同一个大补丁中，没有先规范化不可见字符，也没有按字符串构造方式核对补丁的实际字节内容。

防止规则 → 含 CR、Tab 或多层反斜杠的文件先只读定位；确认是转义损坏后，先机械恢复字面反斜杠。普通 Markdown 与 LaTeX 分开提交小补丁；使用 `String.raw` 时不得沿用普通模板字符串的反引号转义写法。每次补丁失败后必须确认没有部分写入再继续。

### 2026-08-24 · apply_patch 失败仍可能留下部分写入

现象 → 一个同时修改多个文件和多个 hunk 的补丁报告失败后，`.gitignore` 没有创建，但排在失败点之前的 `AGENTS.md` 禁止项已经写入。AI 最初只检查首个目标文件，错误地判断整个补丁没有部分写入。

原因 → AI 把补丁失败误当成事务性回滚，没有逐一检查补丁涉及的所有文件和所有先行 hunk。

防止规则 → 不假设 `apply_patch` 失败具有原子性。跨文件修改优先拆成单文件小补丁；任何失败后必须检查该补丁涉及的每个文件、Git diff 和目标文本，再决定重试内容，避免重复写入或漏记状态。
